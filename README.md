# Домашняя работа № 2 — MongoDB: ShopCatalog

## 1. Окружение и запуск

Решение выполнено на JavaScript для `mongosh` и MongoDB **8.0.30**. Используется replica set `hw2rs` из трёх узлов (
`m1`, `m2`, `m3`): один `PRIMARY` и два `SECONDARY`. Функции реализованы в `solution.js`; исходные `compose.yaml`,
`lab.js` и контрольные данные не изменялись.

Запуск из корня проекта:

```bash
docker compose up -d
docker compose run --rm lab reset
docker compose run --rm lab fixtures
docker compose run --rm lab all
```

Отдельные проверки: `lab data`, `lab index`, `lab purchase`, `lab failover` (через `docker compose run --rm`). Каждый
сценарий сам подготавливает данные. Полные фактические результаты, включая планы запросов и счётчики, сохраняются в *
*`results/results.json`**. После итогового `all` команду `reset` повторять не нужно: она очищает результаты опытов.

## 2. Модель данных и запросы

В `products` находятся товары с текущей ценой `price` (Decimal128) и массивом `variants` — размерами и остатками. В
`orders` каждый заказ хранится отдельным документом, а его позиции — во вложенном массиве `items`. Позиции относятся к
одной покупке и обычно читаются вместе. История пользователя может расти, поэтому заказы удобнее фильтровать и
сортировать как отдельные документы. `items.price` — **цена на момент покупки**, а не текущая цена из каталога.

Валидатор `products` настроен как `strict/error`: проверяет обязательные поля, BSON-типы, неотрицательные цену и
остатки, структуру вариантов и отсутствие повторяющихся размеров. В сценарии `data` корректная вставка проходит;
строковая цена и отрицательный остаток отклоняются **валидатором с кодом 121**.

В `searchProducts` использован `$elemMatch`, чтобы размер и достаточный остаток относились к **одному варианту**. Товары
возвращаются полностью, по `_id` по возрастанию, с `simple` collation. Проверки:

| Запрос                                     | Результат по `_id` |
|--------------------------------------------|--------------------|
| `clothes`, L, 2                            | B, C               |
| `clothes`, M, 5                            | A                  |
| `accessories`, L, 3                        | D                  |
| `clothes`, L, 99                           | `[]`               |
| После пополнения A/L до 2: `clothes`, L, 2 | A, B, C            |

`history` отбирает заказы по `userId` и `status`, сортирует по `{createdAt: -1, _id: 1}` и возвращает максимум **20
полных документов**. Второе поле сортировки определяет порядок при одинаковых датах. Проверены разные пользователи и
статусы, равные даты и пустая выдача.

## 3. Отчёт о продажах

Отчёт выполняется **aggregation pipeline**: `$match` (только `paid` и период `[from, to)`), `$unwind` позиций, `$group`
по `sku` с `sum(qty)` и `sum(qty × items.price)`, `$lookup` названия из `products`, сортировка по выручке убыванию и
`sku` возрастанию, `$limit: 5`. Размеры одного товара объединяются, выручка имеет тип **Decimal128**.

Результат за январь 2026 года на контрольных данных:

| SKU | Товар     | Количество | Выручка |
|-----|-----------|-----------:|--------:|
| A   | Футболка  |          3 |  320.00 |
| B   | Рубашка   |          4 |  320.00 |
| C   | Толстовка |          3 |  270.00 |
| D   | Ремень    |          2 |  240.00 |
| E   | Сумка     |          1 |  200.00 |

**Проверка A:** в `sale-start` куплено 2 штуки по 100.00, в `sale-middle` — 1 по 120.00. Итого **3
штуки, `2 × 100 + 1 × 120 = 320.00`**. При равной выручке A и B первым идёт A по артикулу. Проверены включение начала
периода, исключение конца и неоплаченных заказов, пустой период. После изменения текущей цены A на **999.00**
историческая выручка не поменялась: расчёт использует `items.price`.

## 4. Индекс и `explain`

Для истории создан индекс:

```javascript
{
    userId: 1, status
:
    1, createdAt
:
    -1, _id
:
    1
}
```

Поля равенства идут перед полями сортировки (правило **Equality → Sort**). `hint` не применялся. Один и тот же запрос
проверен через `explain('executionStats')` до и после создания индекса на **10 000 неизменных заказов**.

| Вариант       | nReturned | totalKeysExamined | totalDocsExamined | Отдельная SORT |
|---------------|----------:|------------------:|------------------:|----------------|
| До индекса    |        20 |                 0 |             10000 | Да             |
| После индекса |        20 |                20 |                20 | Нет            |

До индекса используется `COLLSCAN` и сортировка, после — `IXSCAN` без отдельной `SORT`. Список `_id` и порядок выдачи
совпали. `FETCH` остаётся, поскольку возвращаются полные документы заказов. Издержка индекса — место на диске и
дополнительные операции при изменении данных. Полные планы: `scenarios.index.artifacts.explain-before` и
`explain-after`.

## 5. Покупка и транзакции

`purchase` списывает **два разных товара и создаёт один заказ в одной сессии и транзакции**. Доступность проверяется
непосредственно в фильтре `updateOne` (`$elemMatch`, `stock >= qty`), списание выполняется через `$inc`. Все операции
используют базу `c` из `transaction(body)` в `lab.js`. Оболочка вызывает `commitTransaction` при успехе и
`abortTransaction` при ошибке.

| Опыт                                    | Результат                                                                                                                          |
|-----------------------------------------|------------------------------------------------------------------------------------------------------------------------------------|
| Успех: A/M × 2, B/L × 1                 | Остатки **10 → 8**, **5 → 4**; создан один `purchase-001` со статусом `created`, текущей датой и историческими ценами 100.00/80.00 |
| Откат: A/M × 2, B/L × 6                 | Первое списание успешно (`modified: 1`), второе отклонено; `ITEM_UNAVAILABLE`, после `abort` остатки **10 и 5**, заказа нет        |
| Повтор того же `operationId`            | Вернулся прежний заказ с исходными датой и ценами, без списания и нового заказа                                                    |
| Тот же `operationId`, другое количество | `REQUEST_CONFLICT`, данные не изменились                                                                                           |

Для повтора сравниваются **значения** `userId`, `sku`, `size`, `qty` с учётом порядка позиций, а не JSON-текст или
текущая цена товара. Повтор остаётся корректным после изменения цены A на **777.00** и перестановки ключей объекта. *
*Атомарность** отвечает за применение всех изменений одной покупки вместе; **идемпотентность** — за отсутствие второй
покупки при повторе уже подтверждённого запроса.

Настройки транзакции из `lab.js`: `readPreference: primary`, `readConcern: snapshot`,
`writeConcern: {w: 'majority', j: true, wtimeout: 10000}`. Отдельные снимки полного `serverStatus().transactions` до и
после успеха и отката сохранены вместе с `host`, `pid`, `localTime`, `uptime`.

| Опыт  | Δ totalStarted | Δ totalCommitted | Δ totalAborted |
|-------|---------------:|-----------------:|---------------:|
| Успех |              1 |                1 |              0 |
| Откат |              1 |                0 |              1 |

Это результаты контрольного прогона без повторных попыток. Счётчики общие для процесса; основные доказательства отката —
`trace`, возвращённая ошибка и полные состояния документов. Файлы результатов содержат отдельные `transactions-success`
и `transactions-rollback`.

## 6. Смена primary

В отдельной базе `hw2_failover` через **один экземпляр клиента** сохранён документ `before` с
`{w: 'majority', j: true}`. Затем выполнен `replSetStepDown`, выбран другой `PRIMARY`, после чего прежний документ
прочитан и записан новый `after`. Оба изменения подтверждены (`acknowledged: true`), документы сохранены,
`sameClient: true`. Фактические роли узлов — в `scenarios.failover.artifacts.failover.before/after`.

Клиент использует URI со списком узлов и `replicaSet=hw2rs`, отслеживает топологию и самостоятельно находит новый
primary. Физическое соединение может измениться. Подтверждение `majority` **не означает**, что любая secondary уже
применила запись: применение изменений на secondary может отставать.

## 7. Шардирование

По условию `orders` распределена по `{userId: 1}`: меньше 2000 — шард **A**, от 2000 до 5000 (не включая 5000) — **B**,
от 5000 — **A**.

- История `{userId: 2500}` опросит **только B**, поскольку известен диапазон ключа шардирования.
- Отчёт `{status: 'paid'}` опросит **A и B**: фильтра по `userId` нет.
- Индекс `{status: 1}` на шардах **не меняет число участников** отчёта, но может уменьшить число локально
  просматриваемых документов.
